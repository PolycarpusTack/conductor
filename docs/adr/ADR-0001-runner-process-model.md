# ADR-0001: Runner process model

Status: Accepted

Date: 2026-07-04

## Context

DAEMON-mode agents run real command-line tools (Claude Code, or a generic
CLI) against a project workspace. The daemon must hand a composed Execution
Payload — an agent system prompt plus step instructions, often several KB of
user- and LLM-authored prose — to a spawned process, then read back success,
failure, streamed output, and cost. SPIKE A-0
(`docs/gpm/state/spike-a0-headless-cli.md`) established the invocation contract
on Windows against `claude` v2.1.199. The dominant risk is command injection:
one backtick or `$(...)` in an instruction executed under `sh -c` would run
arbitrary code with the operator's credentials. Headless `claude -p` also
skips the interactive workspace-trust dialog, so the spawn directory is
implicitly trusted.

## Decision

The runner (`mini-services/conductor-daemon/runner.ts`) builds a process
invocation with these non-negotiables:

- **Argument arrays, `shell: false`.** `runSpawnSpec()` calls
  `spawn(spec.argv[0], spec.argv.slice(1), { shell: false, ... })`
  (`runner.ts`). Instructions are never interpolated into a shell string. The
  generic template runner splits a **server-resolved** command into argv and
  refuses any command still containing unresolved `{{token}}` placeholders
  (`commandToArgv`, `TemplateTokenError`); only a fixed server-owned token
  whitelist is ever substituted (`TEMPLATE_TOKEN_WHITELIST`).
- **Prompt on stdin.** The composed instructions are written to the child's
  stdin in a single write, then stdin is closed (`runSpawnSpec`). No prompt
  ever rides argv — no length ceiling, nothing in the process list, nothing
  shell-parsed.
- **System prompt via a runner-owned temp file.** `buildClaudeSpawnSpec`
  writes the system prompt to a temp file and passes
  `--append-system-prompt-file <path>` (path generated by the runner, never
  templated), falling back to an inline `--append-system-prompt` arg only for
  prompts below 8 KB. The temp file is deleted in `spec.cleanup()`, always
  called in the `finally` of `runSpawnSpec`.
- **NDJSON result, `is_error` over exit code.** For the claude runner the
  authoritative outcome is the last `"type":"result"` line on stdout
  (`parseClaudeResultLine`). `interpretResult` treats a non-zero exit as
  failure (124 = daemon timeout kill, 127 = spawn error) AND treats exit 0 with
  `is_error: true` — or a missing result line — as failure. Exit code alone is
  not trusted.
- **cwd enforcement.** `runSpawnSpec` throws unless given an absolute `cwd`;
  there is deliberately no fallback to the daemon's own `process.cwd()`. The
  workspace resolver (`mini-services/conductor-daemon/workspace.ts`) resolves a
  step's directory from `DAEMON_WORKSPACE_ROOT` and fails a step with a durable
  `workspace_unmapped` error before anything spawns. Because the trust dialog
  is skipped headlessly, cwd enforcement is a security control, not just
  correctness.
- **Deny-by-default write policy.** `stepPolicyForMode` marks only explicitly
  write-capable modes (`develop`, `draft`) as `write`; everything else is
  `readOnly` → `--permission-mode plan`. A belt-and-braces guard throws if a
  readOnly step is ever mapped to a write-capable permission mode.
- **Echo runner is the safety default.** With no `DAEMON_RUNNER=claude` and no
  server command template, `resolveRunnerKind` selects a no-op echo runner that
  proves the protocol without executing anything real.

## Consequences

- Command injection through prompts is structurally impossible on the runner
  path: prose only ever reaches a process via stdin or a runner-written temp
  file, never through a shell or argv.
- Failures are honest: a CLI that exits 0 but reports `is_error` (budget
  exhausted, max-turns) is still a failed step feeding the existing
  retry/backoff/dead-letter machinery.
- The contract is CLI-agnostic. Any tool that reads stdin participates via the
  template runner; `stream-json` parsing is a claude-specific enrichment layered
  on top.
- Cost/session enrichment (`total_cost_usd`, `session_id`) is available from the
  claude result line but is **not** yet persisted as a `StepExecution` row —
  see ADR-0003 (the DAEMON-mode budget/cost gap, TD-018).
- The reliance on undocumented flags (`--append-system-prompt-file`,
  `--max-turns` in v2.1.199) is a known fragility; the real-CLI smoke
  (`bun run smoke:daemon`) is the guard against a future CLI removing them.
